# MODULE-006 service design — prepared, not dispatched

I need the smallest useful authenticated local file service after MODULE-005A is accepted. Start from session/AGENT-INTERFACE.md, FILE-ACCESS-REQUIREMENTS.md and the exact accepted source pin I will supply. This is a design review brief, not authorization to implement/deploy or configure real storage/credentials.

Target: about six agents using find/list/read/save throughout the day. First validate on synthetic POSIX local roots, loopback only; no public exposure, Google OAuth, background index, jobs framework or arbitrary filesystem/shell endpoint. Each operation must have a precise policy, resource and error boundary. Preserve short agent-facing instructions and replies. Separate hard guarantees from best-effort behavior.

Resolve these questions with exact signatures, a small allowed file scope and acceptance tests:

1. Source/root configuration and per-agent read/write policy: validate every operation, including descendants and closest-name hints, without leaking metadata outside permitted scope. Configured source references, not caller-supplied host paths. Shared adapters remain open safely until in-flight work drains.
2. Bounded concurrency and deadlines: how will the service bound accepted connections, request bodies, queued work, per-agent/source work and stuck filesystem operations? A thread timeout does not terminate a blocked syscall or prevent a later write publish. Choose the smallest honest isolation/cancellation strategy; do not promise hard cancellation if it is only a response timeout. Slow-header/body clients need explicit bounds too.
3. Reads: existing read_bytes buffers a limited whole file. Define the minimum bounded range/stream capability needed to consume larger permitted files without mandatory staging or giant base64 replies. Reuse anchored/no-follow helpers; do not introduce a second path resolver. Identify whether range reads need a narrow preceding adapter module.
4. Saves: explain missing-parent creation, no-overwrite defaults and partial side effects. D018 permits a file to have published before a durability error. Never claim blind retries are safe; specify uncertain outcomes and whether request-ID idempotency is implemented now or explicitly deferred. A restart/expiry-limited in-memory cache is not durable idempotency. Do not delete shared parent directories as rollback.
5. Search/list: use accepted strict scan accounting; skipped subtrees mean incomplete coverage. Offset pagination applies only to full bounded folder listings. No fake continuation for large-directory prefix search. Preserve bounded metadata responses and explicit too-large/truncation outcomes.
6. Transport: REST core first, minimal pinned dependencies only if needed; MCP is a thin wrapper after REST acceptance. Describe an actual agent caller path separately from simulated HTTP clients. A loopback test service is not automatically accessible to remote browser teammates. Public transport and real-root/token configuration require a separate reviewed deployment step.
7. Evidence gate: synthetic multi-agent API tests, permission isolation, authentication rejection, malformed/oversize input, saturation/slow operations, interruption/write uncertainty, no fd/temp/memory growth, redacted audit/health, and restart behavior. Stage the larger 10,000-call soak only after a smaller end-to-end smoke passes. Define measurable bounds before testing rather than moving them to fit a result.

Return a minimal implementation brief and clearly deferred features; split only where a real contract/security boundary requires it. No code, installs, credential creation, implementation merge or deployment in this design assignment. I will choose the scope before assigning the team.
